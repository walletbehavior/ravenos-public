# Wallet-history completion capacity

The signed-in Base profile check found six decoded trades and 14 retained transactions, but only one completed ingestion page. Its outgoing direction was still queued. The accounting correctly left profit unknown until the pinned history window completes.

A bounded production read then found 1,116 unfinished analyzed EVM histories, including 160 with recorded trades. No EVM profile in that job census had a matched-cost result. Base had 29 unfinished trading profiles, BNB 24, Ethereum 55 and Robinhood 52. These are intake counts, not qualified wallet-category counts. The query read 46,795 rows in 40 ms and wrote zero. The latest complete hourly provider reservation total was 5,956 against the existing 6,000-request ceiling.

The previous four-job allocation reserved two places for starting profiles and one for background depth. The candidate uses one place for starting profiles, two for background depth and one for normal priority demand. One of the depth places first considers existing profiles with recorded trades. Within each chain, it prioritizes EVM windows where a provider direction is already exhausted. The ordinary depth place continues other unfinished profiles, including those with only transfer or holder evidence. Chain service fairness remains ahead of trade counts; no P&L ranking or public qualification threshold is introduced.

Empty reservations lend capacity, selections exclude wallets already chosen in another lane, cooldowns and atomic leases remain authoritative, and at least one place remains for direct customer demand. Four jobs per run, provider ceilings, page size, receipt validation and complete-window accounting are unchanged. The scheduler cannot turn a partial profile into a qualified category member.

Two regressions reproduced the old allocation failing to select the useful continuation and failing to prioritize finishing a pinned window. After correction, 188 targeted backend cases pass, covering scheduling, chain fairness, empty lanes, concurrency, budgets, receipts, reconstruction, settlement units, privacy and release flags. Query-plan checks cover all three reserved selections and reject correlated rescans. The exact new trading-depth SELECT was captured from the implementation using an adapter that rejects writes, then run read-only against production: one due candidate, 55,655 rows read, zero rows written and 41 ms. Build, security and all 41 public Worker-response checks pass. Production deployment and actual completed-history measurements remain pending.
